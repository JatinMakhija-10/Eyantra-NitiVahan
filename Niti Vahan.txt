Stage 1: Niti Vahan
Welcome, explorers, to Niti Vahan, one of the thrilling themes of eYRC 2026-27! This year you build an autonomous vehicle that treats the rules of the road not as an obstacle, but as its own logic.

What This World Is About
The Disciplined City
Picture a city arena where an Ackermann-steered vehicle has to earn its way through traffic reading lanes, holding at junctions, signalling its turns, and never crowding a neighbour’s space. Beyond just following rules, the Vahan is defined by its deep civic sense: because it constantly predicts its own future path, it never makes the sudden, selfish moves that cause others to panic.

The Mission
The core task is pick-up and drop-off: collecting a passenger and threading it through the arena while obeying every traffic rule along the way. Stage 1 is about proving this capability in simulation.

The Challenge
Your mission is to bring this disciplined driver to life in simulation first, then on real hardware:

Encode the traffic rulebook as mathematical constraints that a predictive control system can plan against.
Generate a disciplined path that stops at junctions, signals turns, and completes milestones with minimal rule violations.
Maintain dynamic stability while respecting the vehicle’s physical limits when navigating between locations.
Execute precise parking within a designated zone to complete the route.
It’s about proving that smart control logic can produce safer, more orderly movement through the city.

The Abilities You Will Build
Domain	Skills
Perception	Camera-based lane detection, junction and traffic-signal recognition
Planning & Control	Predictive path planning under traffic-rule constraints, Ackermann-steering dynamics, stable path tracking
Decision-Making	A layer that governs when to proceed, hold, or divert toward the parking zone
The Two Stages
Stage 1 - Simulation Challenge

Build and validate lane detection, lane switching via obstacle avoidance, sign detection, and traffic-rule compliance.

Stage 2 - Hardware Build

Realize the same pick-up and drop-off task on a physical platform.

Win Condition
A robot that can navigate the arena by following lanes, avoiding collision, and parking in the designated area.

This is your starting point. Everything you build across both stages - the lane keeping, the junction discipline, the parking - traces back to the mission laid out here.

1. Miniconda
In this section we install Miniconda, and in the next section we use it to create a Python 3.10 virtual environment.

We will be using Python 3.10 in this theme. You don’t have to install Python separately - it is installed into the theme’s environment for you in section C.

That is expected and is not the version this theme runs on - the Python 3.10 environment is created separately in section C.

Conda is a package management system, created specifically to assist working with Python packages in a cross-platform fashion. Conda also has the concept of a virtual environment, which is an independent, self-contained install of Python and packages.

2. Installation of CoppeliaSim
In this section we install the CoppeliaSim robotics simulation platform.
The robot simulator CoppeliaSim is based on a distributed control architecture: each object/model can be individually controlled via an embedded script, a plugin, a ROS or BlueZero node, a remote API client, or a custom solution. This makes CoppeliaSim very versatile and ideal for multi-robot applications. Controllers can be written in C/C++, Python, Java, Lua, Matlab or Octave.
CoppeliaSim is used for fast algorithm development, factory automation simulations, fast prototyping and verification, robotics related education, remote monitoring, safety double-checking, as digital twin, and much more. You can find a feature overview here.
It can be used as a stand-alone application or can easily be embedded into a main client application: its small footprint and elaborate API makes CoppeliaSim an ideal candidate to embed into higher-level applications.

Niti Vahan
Stage 1

Task 1A
Task 1A - Submission
Plagiarism check

Every submitted file is checked with plagiarism-detection software. A plagiarised submission may lead to disqualification of the team.

Grading
Task 1A carries 20 marks, which is split across the two things ackermann_wheel_angles() has to get right. Firstly not blowing up at delta = 0, and returning the correct pair of angles everywhere else.

Component	Marks	How it is scored
delta = 0 case	5	Must return (0.0, 0.0), within tolerance
0.523 > delta > -0.523 cases	15	1.5 marks each, for 10 angles picked at random on every grading run
Returning the correct pair of numbers with left and right swapped scores zero on that case, even though the two values themselves are right.

A result is accepted within a tolerance of 0.1 radians of the expected value.

The 10 angles are different every time

There is no fixed set of test angles. The ten test angles are generated at random each time your submission is graded. So a solution that hardcodes or special-cases particular inputs will not reliably score. There is no way to know the exact angles in advance; only a correct implementation of the geometry scores consistently.

Submission Procedure
1. Self-check locally
Before submitting, run your own file directly and sanity-check it against what you derived on paper - see Self-Check Before You Submit on the instructions page.

2. Rename your file
Your completed boilerplate must be renamed to exactly NV_Task1A.py before you submit it.

3. Upload
Upload NV_Task1A.py directly on the eYRC Portal - Task 1. No zipping, no result file - just the one .py file.

The filename is part of the submission

The file must be named exactly NV_Task1A.py - capital N, capital V, an underscore, then Task1A.py. A submission with any other name is rejected before grading even begins, and you will need to rename and resubmit it.

Your file is imported directly and ackermann_wheel_angles() is called with the test angles described above. If the function is missing, the file fails to import, or it raises an exception on a given angle, that case scores zero - it does not stop the rest of the run.

What the Grader Tells You
After grading, the portal shows a remark. Here is what each one means.

Remark contains	What it means	What to do
delta=0 case: passed (5/5 marks)	ackermann_wheel_angles(0) returned (0, 0)	Nothing
delta=0 case: failed (0/5 marks)	It returned something else, or raised - often a division by zero	Handle delta = 0 as its own case before dividing
Random angle cases: N/10 correct	How many of the ten random angles landed within tolerance	If N is low but not zero, your formula is close but off - check you used the kingpin track, not the full wheel track
Random angle cases: 0/10 correct	No angle matched. Usually the left and right values are swapped, or both wheels got the same angle	Check the order of your return values, and that the two angles actually differ
Submitted file is named 'X', but it must be named exactly 'NV_Task1A.py'	Wrong filename	Rename to NV_Task1A.py and resubmit
Expected exactly one file in submission/	More than one file was uploaded	Upload only NV_Task1A.py - no zip, no extra files
ackermann_wheel_angles() not found in submitted file	The function was renamed or deleted	Keep the name exactly as shipped
Exception occurred while evaluating submitted file	The file could not be imported - a syntax error, or an import of a package the grader does not have	Run python NV_Task1A.py yourself first; it must run cleanly using only math and numpy

Task 1B - Instructions
Learn this first

Read PID Controller and Stanley Controller before you start. Either will solve this task - you pick one. P Controller is the groundwork for both.

Aim
Fill in the two functions of the Task 1B boilerplate so that the Ackermann vehicle in CoppeliaSim moves into whichever lane it is asked for while the simulation is running, and holds it until asked for the other one.

The Problem
The vehicle drives along a straight two-lane road at a constant speed the harness sets. The lane it should be in is asked for during the run, and your controller has one job: steer to whichever lateral position it is currently being asked for, and stay there.

The lane can change at any moment, any number of times. The vehicle is never on the target when a change happens - that is the point. Both the lateral offset and the heading have to be corrected, every time.

You do not detect anything here. The vehicle’s position and heading are read from the simulator and handed to you; lane detection from a camera is Task 1C.

Which controller

PID on lateral error will solve this, and so will Stanley. A plain P controller can converge too, but it tends to overshoot and weave, which the marking scheme penalises.

The Functions You Implement
1. ackermann_wheel_angles() - copied from Task 1A
Paste your Task 1A implementation in unchanged. It is not marked again; it is here because the control loop needs it to turn one steering angle into the two front-wheel angles the joints take. The WHEELBASE and TRACK_WIDTH constants it reads are declared near the top of the file, as before.

def ackermann_wheel_angles(delta):
    ...
    return left_wheel_angle, right_wheel_angle

2. compute_steering() - the controller
Called once per simulation step. It receives the lane to head for and the vehicle’s current measurements, and returns one number:

def compute_steering(target_y, current_values):
    ...
    return steering

target_y is a float in metres and can change between calls. current_values is a dict:

Key	Meaning
y	current lateral position, in metres
yaw	current heading, in radians, 0.0 when aligned with the road
speed	current forward speed, in m/s
dt	seconds elapsed since the previous call
t	seconds since the run started
Return a steering angle in radians, where positive turns the vehicle left - and therefore toward smaller 
y
y. Get this the wrong way round and your controller drives away from the lane, smoothly and confidently.

You need	Compute it from
Cross-track error	current_values["y"] - target_y, written this way round so a positive error asks for a left turn
Heading error	-current_values["yaw"], since the road runs straight
Speed, for the Stanley denominator	current_values["speed"]
Timestep, for the I and D terms	current_values["dt"]
The harness clamps what you return to the steering limit before passing it to ackermann_wheel_angles(), so a large value is safe - but a controller that relies on being clamped is not a controller.

Use the dt you are given

dt is measured, not assumed. Hard-code a timestep and your integral and derivative terms are both wrong - see the PID page.

Keeping State Between Calls
compute_steering() is called fresh each step, so anything in a local variable is gone by the next call. A PID controller has to remember its accumulated error and previous error: keep those in globals inside the implementation block and reach them with a global statement. Stanley needs none of this - it works from the current measurements alone.

Add as many helpers and globals as you like, above the END OF YOUR IMPLEMENTATION line, and list them in the file header.

A lane change is not a fresh start

Nothing is reset when the target changes - your integral term carries straight across the switch, wind-up and all. Check the second and third lane change, not just the first.

Rules
Read this before you start writing code

Write code only inside the ADD YOUR IMPLEMENTATION HERE block. Everything outside it must stay exactly as shipped.
No print(), plotting or input() inside either function when you submit. They are called hundreds of times per run, and the terminal belongs to the lane input.
No sim.* calls. Your function reads its arguments and returns a number; the harness owns the simulator. Placing the vehicle where you want it is not solving the task.
Do not rename the file or either function, or change what they return.
Return a plain float from compute_steering() and a pair of floats from ackermann_wheel_angles(). None or a string crashes the run; NaN does not crash it but makes every later row worthless.

Grading
Task 1B carries 30 marks. Your submitted trajectory is read back and every lane change in it is scored, with the marks split evenly between them.

Component	Marks	How it is scored
Convergence	18	The vehicle reaches the new target_y within 0.02 m and is still inside that band for the last 3 seconds of the segment
Settling time	6	Time from the change until it is inside the band and stays there: full marks at 25 s or less, none at 45 s or more, tapering in between

Why holding the lane matters

Convergence is judged on the end of each segment, not the closest approach. A controller that crosses the target and then oscillates around it has not converged, even though it touched the right value on the way past - see Tuning.

The Function You Implement
detect_lane() is the only function you write. It receives one frame and returns one dictionary:

def detect_lane(frame):
    ...
    return {"center_x": center_x, "lane": lane}

Key	Type	Meaning
center_x	int	x-pixel of the lane centre in this frame, or -1 if the lane could not be found
lane	str	"left", "right" or "unknown"
Which lane is which. The dashed white line divides the two lanes, so the side of it that the vehicle is on decides the answer:

The dashed centre line is…	lane
to the right of the vehicle	"left"
to the left of the vehicle	"right"
not identifiable in this frame	"unknown"
Return "unknown" and -1 honestly when a frame defeats your detector. A wrong answer and a missing answer score the same, and a detector that reports failure is far easier to debug than one that guesses.

Frame Resolution and Coordinates
The clips are 640 x 480, and center_x is an absolute pixel column in the frame as you received it. The evaluator compares it against a ground truth measured in those same pixels, so the number only means anything in them.

Report the answer in the frame’s own coordinates

Inside detect_lane() you may resize, crop or warp as much as you like - but convert the answer back before you return it.

Found the centre in a 320 x 240 copy? It is half the value it should be. Scale it back up.
Read it off a bird’s eye view? That is a warped coordinate, not a frame one. Map the point back through the inverse of your perspective transform (cv2.perspectiveTransform with the inverse matrix).
Do not re-encode, resize or re-compress the clip files themselves. The evaluator checks every clip is 640 x 480 and refuses to grade a dataset that is not, because every correct answer would be shifted sideways.
Keeping one fixed resolution is what makes the same tolerance fair for everyone, whatever method you chose.

Adding Helper Functions
You are not expected to fit everything into one function. Add as many helper functions and global variables as you like - put them below detect_lane() but above the END OF YOUR IMPLEMENTATION line, and call them from detect_lane():

def detect_lane(frame):
    ...
    yellow_x, white_x = marking_positions(frame)      # your helper, defined below
    ...
    return {"center_x": center_x, "lane": lane}


# ---- helpers, still inside the implementation block ----

def marking_positions(frame):
    ...
    return yellow_x, white_x

Defining a helper after detect_lane() is fine - Python resolves the name when the call actually happens, not when the file is read. What matters is that the helper sits inside the implementation block and that detect_lane() reaches it: the evaluation script only ever calls that one function, so anything it does not reach is dead code.

List any helpers and globals you add in the file header at the top of the script.

Rules
Read this before you start writing code

Write your code only inside the block marked ADD YOUR IMPLEMENTATION HERE. Everything outside it - validate_result(), draw_overlay(), process_video(), main() - must stay exactly as shipped, because the evaluation script depends on it.
No display or printing inside detect_lane(). No cv2.imshow(), cv2.waitKey(), cv2.imwrite() or print(). The function computes and returns, nothing else. All visualisation belongs in draw_overlay(), which process_video() already calls for you when you pass --show.
Do not rename the file, the function, or the keys of the returned dictionary.
Helper functions and global variables are welcome, but they must live inside the marked block and be reachable from detect_lane().

What Is Actually New
You have already written both halves of this task. What is new is making them work together.

Task 1C	Task 1B	Task 2A
Where the input came from	a recorded video file	the simulator, as ground truth	the vehicle’s own camera, live

That is why a detector that scored well on the Task 1C clips can still drive straight off the road.

The camera returns a raw byte buffer and a resolution. It does not return an image. The boilerplate connects, looks up the handles once, and turns that buffer into a BGR frame for you.

Why it is given: The buffer's row order and channel order are both wrong for OpenCV. Neither mistake raises an error. You would end up debugging a detector that never saw a correct image.

Stage 1 - The frame (provided)
You do not write this part. task2a.py connects to the simulator and looks up every handle once, before the loop starts. It then hands detect_lane() a corrected BGR frame. You only need to know that the frame is ready to use.

Why is this part given to you? The camera read is the only call in this task that does not return something usable straight away. Its problems are also silent. Each one gives you a detector that seems to work, on a frame that is wrong:

What read_frame() does	What would go wrong without it
sim.handleVisionSensor(...)	This scene’s sensor is in explicit-handling mode, so it renders only when asked. Skip this call and every read returns the same frame for the whole lap. Your vehicle then steers on a picture of where it started
cv2.flip(frame, 0)	The buffer’s first row is the bottom of the image. Without the flip, the road comes out upside down, and the lane appears to bend the wrong way
cv2.cvtColor(..., RGB2BGR)	The buffer is RGB, but OpenCV assumes BGR. Without the swap, every HSV threshold you tuned in Task 1C picks the wrong colour. On this arena, an HSV yellow mask finds zero pixels instead of thousands
Read the function anyway. The ZMQ Remote API page explains what it does, and you will need the same ideas in Task 2B.

Look at your first frame before writing anything else

Call cv2.imwrite('frame.png', frame) once, outside detect_lane(), and open the image. If the frame looks wrong, every later step will look broken too. Checking it first takes a minute.

The shape of the file
The boilerplate has two halves, split by a marker line. Above the marker are the two functions you write. Below it is everything else: the connection, the handle lookup, the camera read, the four joint writes and the loop itself. You are not marked on anything below the marker.

def detect_lane(frame):
    # Stage 2 - your Task 1C detector, extended
    return None                       # anything compute_control() can use

def compute_control(detection, stop_requested):
    # Stage 3 - your Task 1B controller, your Task 1A split, plus the stop rule
    return 0.0, 0.0, 0.0              # (left angle, right angle, speed)

The loop that calls them is already written:

while sim.getSimulationState() == sim.simulation_advancing_running:
    frame = read_frame(sim, handles)
    if frame is None:
        continue
    stop_requested = bool(sim.getInt32Signal('NV_stop'))
    detection = detect_lane(frame)                                   # yours

You can add helper functions. Put them above the marker, next to the two functions, and call them from there.

Two things the harness owns, and you must not

The harness owns starting and stopping the simulation, and where the vehicle is. Your script only reads the camera and drives the joints.

Do not call sim.startSimulation(), and do not call sim.setObjectPosition() on the vehicle. Either one fights the harness for control of the run. Placing the vehicle yourself is also not solving the task. The evaluator reports these calls when it finds them in your file.

Stage 2 - Detection, extended
This is detect_lane(), the first function you write. It receives the frame and returns whatever compute_control() needs. That can be a tuple, a dictionary or your own class. The two functions only have to agree with each other.

Your Task 1C detector answered two questions: where is the lane centre, and which lane am I in. A controller cannot use either answer directly. It needs to know how far off the vehicle is right now. That takes two numbers:

Signal	What it means	Where it comes from
Cross-track error 
e
e	how far the vehicle is from the lane centre, sideways	the lane centre you already compute, compared with the vehicle’s own axis in the image
Heading error 
ψ
ψ	how far the vehicle is pointing away from the direction the lane runs	the slope of the curve you fitted, not its position
The heading error is the part Task 1C never asked for. It is also why the Lane Detection page tells you to fit a curve instead of finding only a centre point. A fitted curve gives you a slope at any row you choose. On the bird’s-eye view, its second-order term also tells you how sharply the road is about to bend.

Pixels are not metres

Your Task 1B controllers were tuned against an error in metres. The camera gives you an error in pixels. The two are not interchangeable. A gain that was stable in Task 1B will be far too large or far too small here.

You have two options. Re-tune the gains against pixel error, or convert the error to metres first. Converting is the better habit. In a bird’s-eye view the scale is constant, so a single number converts one into the other. Whichever you pick, know which units your controller is working in.

Stage 3 - Control
This is compute_control(), the second function you write. It returns exactly three numbers, which go straight to the joints:

Return value	Units	Convention
left_angle, right_angle	radians	the two front-wheel angles. The scene’s steering joints are positive to the left. Nothing is clamped for you, and the vehicle’s limit is 45°
speed	rad/s, both drive motors	0.0 holds the vehicle still
Two pieces of your earlier work meet here:

compute_steering() from Task 1B turns an error into one steering angle.
ackermann_wheel_angles() from Task 1A splits that angle into the two angles the joints take.
Both carry over almost unchanged. Only two things are different: where the error comes from, and what units it is in.

Stanley is worth a second look here. It is built from exactly the two signals a camera gives you: cross-track error and heading error. That is why it is a common choice for camera-based lane keeping. PID on cross-track error alone will also drive the vehicle. But PID has no term that knows which way the road is turning.

Staying in Your Lane
The vehicle must hold the middle of the lane it was placed in, for the whole lap. Most of the marks are here.

Staying on the correct side of the dashed line is not enough. The evaluation measures your distance from the centre of your lane. That centre is surveyed from the painted road edges and the divider. It is not taken from any reference lap. You get credit only for the part of the lap you drive close to it. Weaving from line to line inside your lane loses marks. So does riding the boundary.

You do not choose the lane, and you do not place the vehicle. The evaluation puts the vehicle in one lane and runs your script for a lap. It then puts the vehicle in the other lane and runs your script again. Both laps have to work. A pipeline that quietly relies on the boundary being on one particular side loses most of its score.

This affects how you write the loop in two ways:

Do not hard-code a lane. Work out which lane you are in from what the camera sees, as in Task 1C. Seen from the other lane, the arena looks mirrored.
Do not steer differently depending on which lane you think you are in. Use one controller that follows whichever lane the detector reports. It is simpler, and it does not fail when the detector is briefly wrong.
The measurement is made on the portal

The tool you run only records where the vehicle went. The geometry it is judged against stays on the server. So aim for the middle of the lane.

Stopping When You Are Told
At two places on each lap, the vehicle must come to a complete stop. It waits about five seconds, then carries on in the same lane.

You do not need to work out where those places are, and you must not try. The evaluation watches the vehicle’s position. When the vehicle reaches a stop point, the evaluation raises a flag. Your loop only has to notice the flag and obey it.

How the flag reaches your code
The flag is an integer signal in the simulator, named NV_stop. The boilerplate reads it once per iteration. It passes the value to you as the second argument of compute_control():

def compute_control(detection, stop_requested):
    left, right = ackermann_wheel_angles(steering_angle)  # your Task 1A split
    if stop_requested:
        return left, right, 0.0       # hold still - steering can stay as it is
    return left, right, CRUISE        # drive normally

You do not need to read or touch the signal yourself. In case you are curious: sim.getInt32Signal('NV_stop') returns None until the signal is first set. The boilerplate treats “not set” as “not stopping”, so your first few frames behave correctly.

The flag is a level, not a pulse
You do not time the stop. The evaluation raises the flag and keeps it raised for the whole stop. It lowers the flag when the wait is over. So your rule is simple:

NV_stop	What your vehicle must be doing
1	stationary
0 or None	driving, in its lane
Four things follow from this. Each one costs marks if you miss it:

Stop promptly. You have a moment to slow down, not a hundred metres. The flag is read once per iteration. If detect_lane() is slow, you see the flag late, and you stop late.
Keep remote calls to a minimum. While the simulation is running, each remote call waits for the next simulation step. On this scene that takes 6-10 ms, and every call pays it. To keep the loop quick, make fewer calls. This is also why the boilerplate looks up its handles once, not every frame. See Performance.
Keep returning values while stopped. compute_control() must still return all three numbers, with a speed of 0.0. Do not raise an error, and do not block inside it with a sleep. Either one stops the loop from seeing the flag drop.
Resume in the same lane. The flag dropping is not a fresh start. You are mid-lap and in a lane, and the detector should still know which one.
Do not tie stops to time or distance

The flag is raised based on where the vehicle is, not on how long it has been driving. Say you write “stop after 12 seconds, then again after 30”. That works at the speed you tested at, and fails at any other speed. Guessing the locations does not help either. Read the signal.

How It Is Graded
Task 2B carries 40 marks, split across four components:

Component	Marks	How it is scored
Sign labels	15	Every sign your detect_signs() finds is matched against the ground truth for that image, by label.
Sign area	10	For every sign matched above, how close its area is to the true area (see the tolerance below). A wrongly-labelled sign scores 0 here too; there is nothing correct to compare its area against.
Obstacle presence	10	Whether present matches the ground truth, across every image.
Obstacle area	5	When present was correctly True, how close area is to the true area.
Area tolerance. Two different but genuinely correct implementations will not report the exact same pixel count - different colour thresholds and morphology legitimately measure a sign or the obstacle slightly differently. So area is scored with the same kind of tolerance band as Task 1C’s lane centre, just in percentage terms instead of pixels:

Error against the true area	Credit
within 15%	full
within 35%	half
beyond 35%	none
Sign matching is set-based, not positional. detect_signs() returns a list with no fixed order or count, so each image’s predicted labels are matched against its true labels as sets. Every correct label is a match, every true label your list is missing is a miss, and every label in your list that shouldn’t be there is an extra. Both misses and extras count against the 15 marks the same way. Returning every possible label on every image to guarantee you never “miss” one scores just as badly as never detecting anything, because every image now carries several extras.

Evaluation happens in two places, and only the second one counts towards your score:

Where	On which images	What it is for
On your machine, with the evaluation tool	the public images you were given	Your own feedback - and a check that your code won’t crash on the real grader
On the portal, after you submit	a private set of images you have never seen	Your actual marks
The local tool does not show you a score

eyantra-autoeval evaluate --task 2b prints a table summary of assets detected in every public image, not marks. Its job is to catch a submission that would fail or hang on the real grader before you upload it, not to preview your grade. Use it to confirm your detector runs cleanly and returns sensible results. Your actual score only appears on the portal.

Task 2C - Instructions
You write the manoeuvre, not the vision

Everything to do with the camera is done for you in task2c.py: finding the ArUco marker, working out from it where the vehicle is relative to the bay, and splitting your steering across the two front wheels. You are handed the vehicle’s position and heading every frame. Your job is the parking manoeuvre - deciding how to steer and how fast to drive to get into the bay.

Worth having open: PID · Stanley · Ackermann Steering

Aim
The vehicle is on the road, short of two parking bays that sit to its right. Steer it into the target bay so that it ends up on the bay’s centre line, parallel to it, and stopped in the middle.

The Scene
Task_2C.ttt has two parking bays side by side to the right of the road. Their long axis runs along the road, so a parked vehicle ends up parallel to it.

Bay	Marker	Where it is, from the spawn
0	id 0	0.22 m to the right, nearer the road
1	id 1	0.44 m to the right, further over
Each bay has an ArUco marker standing at its head, facing back down the road. The vehicle is spawned on the road, parallel to the bays, about 1 m short of the markers and to their left. You choose the bay when you run the script - --bay 0 or --bay 1 - see Setting Up.

The bays are 0.22 m wide and the vehicle is 0.18 m across - about 20 mm to spare on each side. There is very little room to arrive crooked.

Replace the caution above with this once images/arena_setup.png is in place:

Task 2C scene: the vehicle on the road, with two parking bays and their ArUco markers ahead and to its right
Figure 1: The Task 2C scene at the start of a run - the vehicle on the road, bay 0 and bay 1 ahead and to its right
Reading the scene from where the vehicle sits:

The road runs straight ahead, and the vehicle starts on it, pointing along it.
Both bays are ahead and to the right, side by side. Bay 0 is the nearer of the two to the road; bay 1 is one bay further across.
Each bay is a long, narrow slot running the same way as the road. You drive into it forwards, and it only fits the vehicle when the vehicle is lined up with it.
The marker stands at the far end of each bay, facing you. It is what the camera measures everything from, which is why it has to stay in view the whole way in.
What You Are Given
Every frame, parking_manoeuvre() receives pose - where the vehicle is, relative to the target bay:

Key	Unit	What it is
lateral	m	Sideways offset of the front axle from the bay’s centre line. Positive = the vehicle is to the left of it; 0 = on it
heading	rad	Which way the vehicle points, relative to the bay’s long axis. 0 = parallel. Positive = turned left
forward	m	Distance along the road from the vehicle’s centre to the marker line. It shrinks as you approach
bearing	rad	Where the marker appears in the camera view. 0 = straight ahead, positive = left
pose is None on a frame where the marker was not seen.

Every angle and offset is positive to the left, the same convention as steering in Task 1. Two distances along the road are given as constants in the file:

Constant	Value	Where the vehicle’s centre is
BAY_MOUTH_FORWARD	0.37 m	at the entrance of the bay
BAY_MIDDLE_FORWARD	0.19 m	in the middle of the bay - where it should stop
What You Write
One function:

def parking_manoeuvre(pose):
    ...
    return steering, speed, parked

Return	What it is
steering	Steering angle in radians, positive turns left. Split across the two front wheels and clamped to 45° for you
speed	Drive-motor velocity in rad/s. Positive drives forwards; 0.0 holds the vehicle still
parked	Return True once the vehicle is parked. This stops the vehicle and ends the run
Add as many helper functions and globals as you like, inside the implementation block. A global is how you remember something between frames - the last pose you saw, for example.

Why Pointing at the Marker Is Not Enough
The obvious manoeuvre is to steer so the marker stays straight ahead (bearing = 0) and drive until you are close enough. It does not park the vehicle.

The bays are to the right of the road, so pointing at the marker brings the vehicle in on a diagonal. It arrives near the marker, but turned about 12° for bay 0 and 23° for bay 1 - and a car crooked by that much does not fit a bay with 20 mm to spare. It ends up straddling the line.

Parking means getting both numbers to zero by the time you arrive:

lateral = 0 - on the centre line, not beside it
heading = 0 - parallel to the bay, not pointing across it
That means crossing over to the centre line early, then straightening up before the bay mouth. This is the whole of the task, and there is more than one good way to do it.

A starting point

Pick a point on the bay’s centre line some way ahead of the vehicle, and steer towards it rather than the marker. As the vehicle closes on the line, that point comes straight ahead and the vehicle straightens out on its own. How far ahead to put that point - and whether it should change as you get closer - is yours to work out.

What a Good Park Looks Like
A good park is three movements run together, and the two bays are the same three movements at different sizes.

1. Cross over to the centre line - early. The vehicle is spawned to the left of both bays, so the first job is to get sideways, onto the target bay’s centre line. Do it while there is still plenty of road left: far out, a turn across the road costs nothing, but close in there is no room left to correct.

2. Straighten up before the bay mouth. Arriving on the line is only half of it - the vehicle also has to be parallel to the bay when it gets there. Turning back straight takes distance, so it has to start before forward reaches BAY_MOUTH_FORWARD, not at it.

3. Creep in and stop in the middle. Slow down for the last stretch and stop when forward reaches BAY_MIDDLE_FORWARD, with the vehicle square in the bay and the same gap to the line on each side.

The two runs below show that done with the reference solution. Watch where the vehicle turns and when it straightens - not just where it ends up.

Bay 0 - the short crossing
Replace the caution above with this once images/park_bay0.gif is in place:

The vehicle parking in bay 0: a gentle turn to the right, straightening onto the bay's centre line, stopping in the middle
Figure 2: Parking in bay 0 - a gentle crossing of 0.22 m, straight by the mouth, stopped in the middle
Bay 0 is 0.22 m across from the spawn. The vehicle turns right by about 25° - comfortably inside the camera’s view - crosses to the line with room to spare, and is already nearly straight well before the mouth. It ends up within a few millimetres of the centre line and under a degree off straight. This is the easier bay; if your manoeuvre does not do this cleanly, it will not manage bay 1.

Bay 1 - the long crossing
Replace the caution above with this once images/park_bay1.gif is in place:

The vehicle parking in bay 1: a sharp turn to the right held across the road, then straightening onto the bay's centre line and stopping in the middle
Figure 3: Parking in bay 1 - twice the crossing in the same distance: turn harder, hold it, straighten late but in time
Bay 1 is twice as far across in the same distance, and everything is tighter. The vehicle has to turn harder - close to 40°, right at the edge of what keeps the marker in view - and hold that angle across the road rather than easing straight back. The straightening comes later and has less room, which is why even a good run finishes a few millimetres off the line and a couple of degrees from straight.

That is the margin the bay leaves you: about 20 mm each side, and the leftover heading uses some of it. A manoeuvre tuned only on bay 0 typically turns too gently here, reaches the bay still off the line, and stops with a wheel over it.

What the two runs have in common

In both, the vehicle is across and straight before it enters the bay, and it only goes slowly once it is lined up. Neither steers at the marker. That is the pattern to aim for - how you get it is up to you.

The Things That Will Bite
Problem	Why it bites
Turning too far	The camera is 95° wide. Turn much more than ~40° across the road and the marker leaves the view - pose goes None, and you have nothing left to steer by
Reacting to noise	Far away, heading is only known to about a degree, and every degree puts lateral out by ~14 mm. Steer hard on every small change there and the vehicle weaves. The pose sharpens as you get closer
Straightening too late	Leftover heading costs bay width: 5° over the 0.17 m length of the car is 14 mm - most of your margin
Straightening too early	Straighten while still off the line and you stay off it
Losing the marker	A single None frame is normal. Decide what to do on one - and what to do if it keeps happening
Stopping short	Stop before BAY_MOUTH_FORWARD and the vehicle is parked on the road
The Rules
Write only inside the implementation block. Everything below END OF YOUR IMPLEMENTATION is relied on by the evaluation.
Do not move the vehicle yourself. No sim.setObjectPosition(). Your function returns a steering angle and a speed; that is the whole interface.
Do not read positions out of the simulator. Everything you need is in pose.
Come to a stop. A vehicle still creeping when the run ends is not parked.

Task 2C - Submission
Plagiarism check

Every submitted file is checked with plagiarism-detection software, and submissions are compared against each other. Code shared between teams is treated as plagiarism and acted on strictly - for the team that copied and the team that supplied it alike, and it may lead to disqualification.

The boilerplate is the same for everyone, so only what you write inside the implementation block is compared.

How It Is Graded
Task 2C carries 20 marks, and the grading happens in two places.

Where	What happens
Your machine	The evaluation tool parks the vehicle in both bays and records each run - a row per sample of where the vehicle was, which way it was pointing, and how fast it was going.
The portal	Those recordings are replayed against the car park’s surveyed geometry and scored.
Your marks come from the portal, not from your own run

The tool you run reports what happened, never how well you did. Upload your recordings to see your marks.

The two runs
The evaluation, not your script, decides which bay to park in. It:

spawns the vehicle and runs your task2c.py into bay 0,
then spawns it again and runs it into bay 1.
The tool chooses the bay itself, by running your script with --bay 0 and then --bay 1 - the same flag you use yourself. Whatever TARGET_ID says in your file does not matter here.

Run	Bay	Share of the marks
1	bay 0 - the near bay	70% (14 marks)
2	bay 1 - the far bay	30% (6 marks)
The two runs are not weighted equally. Bay 0 is the core of the task and carries most of the marks. Bay 1 needs twice the sideways crossing in the same distance, with less room to straighten - it is the harder of the two, and it is where a manoeuvre that is merely good gets separated from one that is precise.

What each run is scored on
Each run is scored out of 20 on the same three components, then weighted as above.

Component	Marks	How it is scored
Parked in the target bay	8	The whole vehicle comes to rest inside the bay it was asked for - no wheel over a line
Alignment	8	How centred and how straight it ends up - offset from the bay’s centre line, and heading against its long axis
Stopped cleanly	4	At rest when the run ends, not still creeping
A run that ends in front of the right bay but outside it scores the alignment component partially and the parking component not at all - being almost in a bay is not parking. With about 20 mm to spare each side, a vehicle that arrives turned by more than a few degrees will have a wheel over the line even if it is centred.
